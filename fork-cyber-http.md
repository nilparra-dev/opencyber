# HTTP assessment tools (phase 3)

`http_request`, `http_replay` and `http_compare` are native tools registered by the built-in cyber plugin. They use the phase 2 evidence database. No public Protocol or Server HttpApi change is required.

## Requests and evidence

Record an explicit engagement first. The following examples are tool inputs, not shell commands:

```json
{ "url": "http://127.0.0.1:8080/api/items/42", "headers": { "Authorization": "Bearer account-a-token" } }
```

`http_request` accepts `url`, `method`, `headers`, `body`, `timeout_ms`, `max_bytes` and `redirects`. Methods are GET, HEAD, POST, PUT, PATCH, DELETE and OPTIONS. A body is UTF-8 text or `{ "base64": "AP8NCoA=" }` for exact binary bytes. GET/HEAD bodies are unsupported. Request bodies are capped at 1 MiB, with at most 64 custom headers.

The request and replay tool schemas describe the body limit without a large `maxLength` keyword. Million-character bounds exceed some providers' constrained grammar budgets, including DeepSeek's. Local schema validation still enforces the text and base64 length limits, and the HTTP transport enforces the 1 MiB byte limit before sending a request.

This schema is shared by all models. Offline regression tests compile the actual request bodies for OpenAI Chat/Responses, Anthropic, Gemini, Bedrock, Mistral, DeepSeek, xAI and compatible endpoints, including Kimi and Gemini model-specific sanitization. They verify request preparation and retained body limits without live provider calls.

Each hop returns an output artifact ID in `evidence`, an execution ID, status, body length/hash and the pinned destination address. Use `evidence` with that artifact ID to read captured response metadata. Its `response_body` references the original entity bytes, including non-UTF-8 bytes. Raw duplicate response headers and the response HTTP version are retained. Bodies are not decompressed automatically; the default request asks for identity encoding.

The input artifact contains the reproducible request parameters. Execution provenance records the runtime, effective scope at entry, tool call, replay source and preceding redirect. Completed response metadata also records the scope used at admission. This is HTTP entity/header capture, not a packet trace: TLS records, TCP bytes, chunk framing, trailers and informational responses are not archived. Host and framing headers are generated by the transport.

Timeout defaults to 30 seconds per hop, including DNS, rate waiting and response handling, and is capped at 120 seconds. Response bodies default to 1 MiB and are capped at 4 MiB. Oversized, incomplete and timed-out responses produce error records instead of complete evidence. No automatic transport retries run. Cancellation aborts the connection; as in phase 2, interruption can leave a `running` record with no terminal output, meaning unresolved rather than successful.

## Scope and pacing

Only these HTTP request/replay tools enforce this policy. Shell, browser, MCP, webfetch and other network clients are unaffected.

- A hostname must be explicitly included; entries do not authorize subdomains. Literal IP URLs may match an included host or CIDR. DNS names do not inherit authorization merely because they resolve into an included CIDR.
- Host/IP/CIDR exclusions take precedence. All DNS answers are checked against IP/CIDR exclusions. The first address, preferring IPv4, is pinned for the socket connection; it is not resolved a second time. There is no automatic fallback to another address. Private and loopback destinations work when included, which supports local labs and internal audits.
- The present manifest scopes hosts/networks, not ports or paths. Including a host permits its ports and paths. The free-text assessment window and `no_dos` declaration remain operator rules, not automated technique controls.
- Before each HTTP hop and each rate admission retry, current scope is reloaded. The shared SQLite budget admits at most one start per `ceil(1000 / max_rps)` milliseconds for a top-level engagement, across child sessions, Locations and local processes. The database timestamps admission after acquiring its write lock, and the capture retains `admitted_at`. It limits admissions, not remote receipt timing, simultaneous open sockets, payload throughput or server-side side effects. A cancelled start consumes its interval. Intervals above 120 seconds are rejected instead of waiting indefinitely.
- TLS verification is explicitly enabled. URL-embedded credentials, non-HTTP protocols, custom Host/framing/connection headers and protocol upgrades are rejected. There is no insecure-TLS switch, proxy configuration or browser cookie jar.

Up to five redirects are followed by default, with a configurable maximum of ten. Every destination is checked again. Cross-origin redirects drop all custom headers; body-preserving redirects across origins are rejected. Standard 303 and POST 301/302 transitions become GET; 307/308 preserve the method and body. At the redirect budget, the last 3xx is returned without following it. Set `redirects: 0` to inspect the first response only.

## Replay and comparison

`http_replay` uses an HTTP output artifact from the same engagement:

```json
{ "source": "output-artifact-id", "changes": { "headers": { "Authorization": "Bearer account-b-token" } } }
```

Changes replace supplied fields. `headers` replaces the entire custom header map; `{ "headers": {} }` makes an anonymous control. Omitted headers reuse the recorded values. URL changes must stay on the original origin. Replays use current scope and pacing, and create new evidence linked to their source. A replay sends real traffic and may repeat side effects.

`http_compare` performs no network activity:

```json
{ "left": "account-a-output-id", "right": "account-b-output-id" }
```

It verifies both stored bodies, then returns status pairs, body equality, lengths, literal header equality and the first differing byte. Header ordering, Date and other dynamic values can cause differences. Similarity alone does not establish an authorization vulnerability. Validate account identity, object ownership, an anonymous control and a correctly protected control endpoint before confirming a finding.

Reporting agents may compare and retrieve evidence, but cannot request or replay. OpenCode permissions also apply to each destination: replay requires both `http_request` and `http_replay`; comparison checks `http_compare` against its artifact IDs. Permission questions use the existing application lifecycle and are outside the network deadline. Raw archives can contain assessment credentials. Model-visible previews mask common credential keys and raw header pairs; the filter is not an exhaustive secret detector. Exported artifacts retain raw bytes.

## Migration and validation

The archive advances from schema 1 to schema 2 by adding the HTTP admission budget table. Existing evidence and notes are preserved. An older phase 2 executable rejects schema 2, so make a private backup before upgrading if rollback is needed. No upstream session migration or generated client change is involved.

Run from `packages/core`:

```sh
bun test test/plugin/fork-cyber-http.test.ts test/plugin/fork-cyber-tool-schema.test.ts test/plugin/fork-cyber-store.test.ts test/plugin/fork-cyber-integration.test.ts
```

The HTTP suite uses only local fixtures: two accounts plus anonymous access on broken/protected endpoints, destination exclusions, DNS pinning, cross-origin credential stripping, redirect methods, binary bodies, response limits, timeouts, cancellation, untrusted TLS and shared pacing across independent processes. The TLS key/certificate under `test/fixture/fork-cyber-tls-*.pem` are public self-signed fixture credentials, never operational credentials.

This phase supplies the HTTP workflow, not HTTP/2, WebSockets, browser traffic interception, mutual TLS or a general request-smuggling transport. Kali execution and browser/proxy integrations remain subsequent phases.

Windows/Bun 1.4.2 validation: the final regression run passed 106 tests across ten Core files, with five existing platform skips. Root `bun run check` passed lint and all 35 typecheck tasks. HTTP and storage suites also passed repeated runs while typechecking was active. These are local fixture checks; Linux CI and compiled-binary validation are separate release checks.
